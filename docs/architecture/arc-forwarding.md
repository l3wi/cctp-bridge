# Automatic claims

Routes between supported EVM and Solana chains with CCTP v2 and destination-forwarding capability default to automatic claim. Eligibility comes from metadata, not a destination allowlist. Source forwarding flags do not gate these routes.

The form retains its current transfer-type controls, summary rows and primary action. One switch controls delivery mode, separate from speed. Total fees bundles app, protocol and forwarding fees. Native source gas remains payable in the wallet. Intent URLs preserve the selected delivery mode and authorized maximum; existing manual burns retain their original mode.

`lib/cctp/forwarding.ts` requests `forward=true` fees, validates the selected tier and computes integer protocol fees with ceiling division plus the medium forwarding fee. Standard forwarding requires a nonzero fee too. For a Solana destination, quotes include recipient setup and the hook requests creation of the owner-derived USDC ATA. Both the quote and burn bind to the same recipient owner. EVM burns use `depositForBurnWithHook`, or `bridgeWithPreapprovalAndHook` when collecting the existing atomic app fee. It rechecks fees after approval, bounded by the authorized maximum. The Standard receipt verifier recognizes both hook selectors while retaining owner, token, amount, fee-transfer, debit and finality validation. Solana burns use the corresponding hook instruction with the existing atomic SPL app-fee transfer. Message account rent covers 428 bytes plus hook length, and the source SOL check includes rent plus the compiled transaction fee. Source-paid receive-exact fees are not used.

Persisted transactions retain delivery mode, fee cap and destination hash. Automatic monitoring continues after attestation readiness and bypasses wallet-switch/manual-claim prompts. Iris `forwardTxHash` is only a submission signal, supporting EVM hashes and Solana signatures. EVM completion requires a successful destination receipt with matching MessageReceived source domain, nonce and message body plus a mint to the intended recipient. Solana completion requires a successful receive_message instruction containing the exact message, a mint of the expected net amount to the owner-derived ATA, and a consumed nonce. Arc system-emitter Transfer events are accepted. Unavailable status stays pending and can be retried; it never requests a replacement burn.

Arc native USDC (18-decimal gas accounting) and ERC-20 USDC (6 decimals) share one balance. Max reads current native balance and gas pricing, reserves twice a 1,000,000-gas budget (approval plus hook burn), and rounds spendable funds down to atomic USDC. It fails closed on unavailable pricing. This conservative reserve is not an execution guarantee if pricing changes before signing.

Validation uses deterministic mocked quotes, wallets and receipts. Funded end-to-end transfers and deployed hook-contract behavior must be checked before claiming live transfer validation on each route.
